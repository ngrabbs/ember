# EMBER Telemetry & Event Dictionary

**Status:** Draft 0.2

This document defines application-level messages generated by EMBER to report spacecraft status, health, mission information, and significant events.

EMBER does not require an operator request to generate routine telemetry or significant event messages. Messages may be generated periodically, in response to an event, or in response to an operator command.

Message IDs, contents, transmission rates, priorities, and reliability requirements are preliminary.

## Message Categories

EMBER uses four primary application-level message categories.

### Periodic Telemetry

Periodic telemetry is generated automatically at configured intervals and does not require an operator request.

Examples include:

- `HEARTBEAT`
- `SYSTEM_STATUS`
- `CURRENT_MODE`
- `POWER_STATUS`
- `THERMAL_STATUS`
- `FAULT_STATUS`
- `PAYLOAD_STATUS`
- `STORAGE_STATUS`
- `COMM_STATUS`

Final update rates are TBD and should be selected based on mission needs, communications bandwidth, and available power.

### Event Messages

Event messages are generated automatically when a significant spacecraft or mission condition occurs.

Examples include:

- `FIRE_DETECTED`
- `MODE_EVENT`
- `RESET_EVENT`
- `FAULT_EVENT`
- `LOW_POWER_EVENT`

Event messages should not wait for the next periodic telemetry interval or require an operator request.

Critical events should be stored onboard so they are not lost when a ground communications link is unavailable.

Transmission priority, retry behavior, acknowledgment requirements, and event queue handling remain TBD.

### Requested Telemetry

An operator may request current or stored information at any time permitted by the spacecraft mode.

REQUEST_STATUS
REQUEST_TELEMETRY
REQUEST_DETECTION_DATA
